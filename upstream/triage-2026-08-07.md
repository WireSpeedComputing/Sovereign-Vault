### #12 — Add richer cutover probe categories · **strongest candidate**

Fully implemented. `tests/sovereign_probes.sh` runs all five categories the issue
names, and the restore verifier consumes them as check K with a second check K2
comparing probe verdicts against the source.

| #12 category | our probes |
| --- | --- |
| positive | `positive.read_current_memories`, `positive.retrieve_context_envelope`, `positive.propose_then_promote` |
| negative | 8 probes, incl. `negative.direct_insert_at_current`, `negative.promoted_content_rewrite`, `negative.audit_trail_is_append_only`, `negative.artifact_not_classified_import`, `negative.grant_on_undeclared_scope`, `negative.non_human_promotes` |
| conflict | `conflict.two_current_wiki_pages_same_path`, `conflict.duplicate_source_artifact`, `conflict.review_queue_holds_contradiction` |
| stale state | `stale.superseded_rows_are_not_current`, `stale.retrieval_acl_drift_is_zero` |
| evidence request | evidence-locator resolution, check C in `tests/verify_restore.sh` |

The design point worth upstreaming with it: **negative probes ATTEMPT the
forbidden write.** "The negative probe was rejected after restore" is only
evidence if something was actually tried. The header of `tests/sovereign_probes.sh`
says so explicitly. Also `stale.superseded_rows_are_not_current` raises if there
are **no** superseded rows at all, so the probe cannot pass vacuously — that
guard is worth generalizing across the probe set.

Depends on nothing unapplied. Ready to offer today.

### #32 — Document Agent Durable-Write Policy and minimum proposal workflow

The issue asks for a policy: *"agents may propose truth; approved workflows
promote it."* We have that **enforced in DDL rather than written as a policy**,
which is strictly stronger and is exactly what the issue's background incident
(an agent mutating a durable page after reading ambiguous language as permission)
calls for.

- `sql/26_propose_then_promote.sql` — `status='current'` unreachable by direct
  INSERT; column default moved to `'proposed'`; the definer functions are the sole
  path to authority
- `sql/03_provenance.sql` — an agent cannot self-attest to `human_direct`
- `tests/23_promotion_guards_negative.sql` — 31 assertions

Two findings from that work belong in the issue: the guard **must not be keyed on
`source_kind`** (caller-declared, so bypassable by assertion — `b6`/`b6b` assert
both evasions), and `promote_memory()` was a **convenience wrapper rather than a
chokepoint** before this, which is the exact failure mode a written-only policy
produces.

Honest caveat to carry: `sql/26` is **not applied** to any deployment, and
`app.promoting` is a session GUC that an unrestricted role can arm. This closes
the accidental path, not the deliberate one.

### #66 — Specify per-field immutability and custody-chain conformance · **high value, currently `status:blocked` upstream**

We have a working per-field mutability implementation. This is probably the
highest-leverage thing we can offer that nobody has asked us for.

- **Per-field matrix, implemented:** `sql/26` freezes authority-bearing fields on
  a promoted record (`content`, `provenance_basis`, `citation`, `source_kind`,
  `source_agent`) while operational fields (embedding, hot-touch, due status,
  metadata, owner, visibility) stay mutable. A candidate at `proposed` stays fully
  editable. That is exactly #66's "lock custody-semantic fields after recording"
  with the candidate/record distinction the issue implies but does not state.
- **Corrections append successors, never rewrite:** `supersede_memory()` /
  `supersede_wiki()` close the predecessor and link the successor.
- **Chain fields:** `supersedes` with a partial unique index preventing two live
  successors for one predecessor (`sql/20`).
- **A second ratchet:** `sql/31_consequential_domains.sql` makes a classification
  addable but never changeable or removable — null → domain is allowed (late
  classification is a strengthening), domain → other is an error.
- **Conformance surface:** `promoted_record_audit` + `verify_promoted_integrity()`
  reporting `match` / `mismatch` / **`unaudited`**.

The `unaudited` state is the part to push hardest. #66 asks for testable
conformance; a two-state verifier converts absence of evidence into evidence in
whichever direction it folds, and every record predating the policy is in exactly
that state on day one.

### #8 — Design least-privilege access model for assistants and UI

Largely satisfied *as a design*, and our most useful contribution is the finding
that it is not wired up.

- `sql/23_identity_capability_enforcement.sql` — private `vault_auth` layer;
  `(issuer, sub)` for a human, `(issuer, client_id)` for an agent surface; agent
  requests require the **intersection** of both; claims trusted only when
  `session_user = 'authenticator'`, so an administrative session fabricating
  claims fails closed and returns `false`, never `NULL`
- `sql/25_public_request_has_capability.sql` — the reachable entry point;
  `SECURITY INVOKER` is load-bearing, because a definer wrapper would rewrite
  `current_user` and invert the property the function exists to protect
- `sql/07_default_privileges.sql`, `sql/05` + `sql/28` — perimeter and default
  privileges
- `sql/30` + `docs/05` — scope model, no global scope kind

**The finding:** nothing calls `has_capability()` or `request_has_capability()`.
Not one policy, function or view. Already stated in our #45 comment; #8 is where
the "inventory of required capabilities by surface" deliverable would actually
close it.

## (b) Worth adopting

### #11 — Candidate source locators and quote-hash fields · **highest priority in this group**

We have a **documented, measured** version of the problem this issue describes.
An evidence-locator audit across the deployment found that categories embedding a
database-checkable reference were 100% resolvable, while **a meaningful minority
of citations are prose "recorded by X in session Y" references with no
independently checkable locator at all.**

Our `citation` column is `NOT NULL`, which proves a string is present — not that
it resolves to anything. `raw_artifacts` carries a payload hash for the whole
item, and `retrieval_units.exact_locator` is a projection-level locator, but
there is **no candidate-level span locator and no quote hash** anywhere in this
branch.

This is a real gap with real evidence behind it. Adopt.

### #52 (partial) — the honest-state vocabulary

Adopt `installed` / `backup_created` / `custody_verified`, plus
`verification_failed` and `verification_skipped` **with a recorded reason, never
representable as verified**. That is the same discipline as our `unaudited` state
and our `not_evaluated` retrieval status, and we should use one vocabulary across
all three rather than inventing a third.

### #7 — Executable source cutover validation bundle

We have the pieces scattered across `import_cutover_scorecard` (`sql/06`),
`scope_authority_report()` (`sql/30`), `retrieval_acl_drift()` (`sql/27`),
`retrieval_embedding_coverage()` (`sql/29`), `compliance_coverage()` (`sql/18`)
and `verify_promoted_integrity()` (`sql/26`). What we do not have is **one query
returning pass/fail rows** across them.

Blocked on the same missing piece as #70 and #72: there is no `session_boot()`,
which #7 lists as a required check. Adopt after that exists, not before.

### #41 — Markdown link-check script

Cheap, and we have a **worse** version of this problem than the issue describes.
`docs/08-contract-version-and-drift.md` cites claims to **file and line number**
(`sql/20` line 147, `sql/27` line 113, `sql/29` lines 49–79). Line references go
stale silently on the next edit and there is nothing checking them.

Worth adopting in a stronger form: check repo-relative links *and* verify that
cited files exist, with a follow-on question about whether line-number citations
should be replaced by symbol names.

### #9 — Synthetic source-adapter examples

We have exactly one synthetic fixture shape (`tests/sovereign_fixture.sql`) and no
`examples/source-adapters/` directory. Lower priority than #11 but the same
family. Adopting even one non-database source shape would test whether the
artifact/disposition model is genuinely source-agnostic or quietly assumes a
row-shaped source.

### #60 — One-way repository boundaries (partial adoption only)

The ADR itself is upstream governance. But the operational half — "deployment
data never lands in the public repo" — is something this branch already practices
with a pre-push sweep, a `pending/` staging directory so unapproved migrations are
not swept into a replay that would prove something untrue, and generic seed labels
in `pending/B` so the migration file stays publishable while the rows stay
deployment data. Those three mechanics are worth contributing to the ADR even
though the repository split is not our decision.
